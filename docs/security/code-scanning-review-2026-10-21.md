# Code-scanning review — ThreatFlux/file-scanner

Reviewed 2026-10-21. Scope: all **24 open alerts (18 CVEs)** retrieved with paginated GitHub API calls. No alerts dismissed, no source changes made. Latest main is `a34604292e7060f45d3c6f10b392c326afe2ead1`.

## Evidence and interpretation

- All 24 open alerts are **Trivy OS package** findings, not Rust CodeQL findings. Latest main CodeQL analysis `1986509420` (2026-10-20) reports **0 results**. This does not prove the application is vulnerability-free.
- Latest main Trivy analysis `1978550289` (2026-10-19) contains 31 SARIF results. The open-alert API returns 24 open alert records; SARIF result count is not the number of open alerts. All 24 most-recent instances point at current main, and complete per-alert instance histories were retrieved. **These cannot be written off as findings from a superseded Debian slim Dockerfile.**
- Baseline main Dockerfile uses `gcr.io/distroless/cc-debian13:nonroot@sha256:e792ab3d241a468a4fd7519ddbbebe66b49b5f365771716ea688ad40b6c6f1c2`, with Rust 1.99 builder. Refreshed Rust/Cargo dependencies alone will not fix these OS findings.
- Inspected published main image `ghcr.io/threatflux/file-scanner:a346042`, index `sha256:e0065caf14177e3679f3a90cdacf080133e9bd3ce203c611f6442dfa58fc9cb5`; pulled/exported amd64 child **by digest**, `sha256:e0a7920868a9d7509bd8cf23b9b9092bd6693276791213955794bdf002972e78`. No image execution was needed. Package status files confirm glibc `2.41-12+deb13u4`, GCC runtime packages `14.2.0-19`, zlib `1:1.3.dfsg+really1.3.1-1+b1` exactly as reported.
- Exported amd64 rootfs contains **no nscd and no setuid/setgid files**. Manifest platforms are amd64 and arm64, no PowerPC. Arm64 filesystem was not exported; absence-based conclusions for arm64 must be confirmed before any blanket dismissal.
- Scanner ELF `DT_NEEDED` entries are only `libgcc_s.so.1`, `libm.so.6`, `libc.so.6`. It imports **getaddrinfo**; it does not import iconv, fopen, strfmon, tdelete, wordexp, DNS debug printers, zlib CRC/gz functions, or dlopen. Source search likewise found no actual calls to these affected interfaces. This supports prioritization, but cannot exclude every indirect/transitive libc path. The Dockerfile comment claiming dynamic zlib linkage is stale for this published binary.
- Debian primary tracker was checked for all 18 CVEs. It currently marks the installed **trixie source package versions vulnerable**, with no stable fixed version published in the tracker. Fixed versions below are **unstable reference versions**, not a recommendation to install sid packages into stable. Debian source-package matching also explains several non-applicable binary-package alerts.

Classification uses two explicit scopes: **TP/package** means an affected component/version is present, not that attacker reachability is proven; **FP/runtime** means a necessary component, architecture, or privileged-execution prerequisite is absent in the inspected deployment; **uncertain** means contradictory version/component evidence prevents a defensible disposition. Totals: **12 TP/package, 10 FP/runtime, 2 uncertain**. Only #266 has a directly evidenced relevant application interface. All FP runtime conclusions are bounded to the inspected image/configuration.

## Remediation plan and acceptance criteria

1. **P2, DNS DoS (#266):** prove actual DNS behavior with current all-feature release in isolated test deployment. Review resolver configuration origin and environment inheritance. Bound search domains/remove untrusted LOCALDOMAIN; test standard lookups and the long-domain condition. Select patched glibc stable backport or a supported Rust resolver if configuration mitigation is insufficient. This is the clearest actionable runtime issue; no critical/high open code alert is present in GitHub's current alert metadata.
2. **P3, OS patch backlog (all TP/package rows):** regularly recheck the exact Debian tracker pages above. Glibc unstable reference fixes: #22/#25/#187 `2.43-3`, #189/#194 `2.43-4`, #204/#205/#206/#207 `2.43-5`, #266 `2.43-6`; GCC #317 reference `14.4.0-3`; zlib #124 reference `1:1.3.dfsg+really1.3.2-1`. These are evidence of fixes, **not stable trixie package availability**. Prefer official trixie backports and refreshed distroless digest. If adopting another runtime, establish ABI/library compatibility instead of mixing sid libraries.
3. **P3, shrink unused runtime components (#317/#124 and uncertain #316/#257):** prove ELF transitive closure for scanner and tini on both architectures. Current scanner needs no zlib or C++ runtime; evaluate supported smaller distroless base/custom runtime assembly, carrying licenses/certificates/NSS/tini and package metadata. Test all-feature file/archive/MCP workflows and DNS. Do not simply delete package status records or replace broad libc functionality to silence findings.
4. **P3, evidence-based FP resolution:** verify both amd64 and arm64 inventories and mounted/runtime assumptions. Record package-content evidence for source fanout and deployment-specific prerequisites. For #317 specifically, [upstream GCC patch](https://github.com/gcc-mirror/gcc/commit/200183d4ab5d57575f3dfebc6af3baf649910b9e) states POSIX memalign implementations avoid the affected rounding; inspect actual library implementation before changing the conservative TP/package label. For #257, [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2026-85091) explicitly links affected-range discussion and introduction commit; resolve contradiction before calling FP.
5. **Rescan the exact new runtime digests for both platforms**, preserving full Trivy JSON and SARIF plus DB metadata. Current workflow only asks for CRITICAL/HIGH and exits 0; reported medium/low metadata must not be treated as complete fresh coverage from that filter. Run an additional all-severity scan for this review and use stable category to resolve alerts through fresh analysis. Record newly observed vulnerabilities separately. Verify GitHub main post-merge state before claiming closure.

No changes to GitHub alert dispositions or Jira were made. A clean CodeQL result is separate from unresolved OS package exposure, and source/ELF absence alone is insufficient to mark every conditional libc issue FP.
